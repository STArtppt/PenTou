# Doc Folder Organize

> Plane B 产品技能。被 skill-runtime 的客户端 runner 加载执行；外部 agent 可读本文件 + 打同一 `/api/*` 数据层，自带 LLM 复现。

## 前置检查

- 探活：`GET /api/health` 返回 `status: "ok"`。

## 输入 / 输出

- 输入 schema：`schema/input.schema.json` — `{ projectId?, planTitle?, lang? }`
- 输出 schema：`schema/output.schema.json` — `{ planDocId, folderId, itemCount, cleanupCount, projectType, candidateCount, notes[] }`

## Workflow（线性）

| # | id | kind | 说明 |
| --- | --- | --- | --- |
| 1 | `inventory` | `api` | 列文档元数据 + 文件夹 + 项目；筛出本项目的归类候选，并审计数据异常 |
| 2 | `prompt` | `transform` | 注入**两套典型结构** + 数量约束 + 清理提议要求，要求模型只输出 JSON |
| 3 | `propose` | `llm` | 客户端调 LLM 产出 `{"projectType","typeReason","items":[…],"cleanup":[…]}`；`projectType` 非法时回退 `knowledge` 并记 note |
| 4 | `plan` | `api` | 按 `projectType` 取典型结构 → 客户端强制数量约束 → `POST /api/documents` 把计划落进 AI 空间 |

## 项目类型与典型目录结构

判定结果与依据 MUST 写进计划正文，用户一眼能看出判成了哪类、判错了就重新生成。

| projectType | 典型目录 |
| --- | --- |
| `dev`（开发项目） | `设计文档` / `开发记录` / `部署运维` / `常见问题` / `运营文档` / `接口文档` / `宣传文档` |
| `knowledge`（知识工作项目） | `1_输入原料` / `2_输出产物` / `3_数字藏馆` |

典型目录 MUST NOT 被无条件创建 —— 只有确实有文档被提议归入的才进计划、才会被建出来。空目录对用户没有价值。

## 数量约束由客户端强制

- 本次**新增**的目录（既不在典型结构、也不在该项目已有文件夹中的）不超过 **3** 个
- 执行完成后该项目的目录总数不超过 **10** 个
- 已有目录数已达 10 时，本次**零新增**，只在既有目录内归类

超限时按承载文档数降序保留，被裁掉的目录对应的归类条目**整条丢弃**（不强行塞进别的目录），
裁剪情况 MUST 如实写进计划的 notes。

> 这些是**计数约束**，而 LLM 对计数的遵守率经验上就不可靠。写进 prompt 是让它往这个方向努力，
> 写进代码才是保证 —— 与「模型可能编出不存在的 docId → 客户端最后一道过滤」是同一条纪律。

## 计划文档批准协议

这是本期唯一「批量且改动既有数据」的操作，因此 MUST 先出计划、经用户勾选批准后才执行。

- 正文每条以 `- [x]` 开头（**默认全部勾选**）；正文开头 MUST 说明「取消勾选即表示不采纳该条」
- **执行时只读复选框、不解析条目文字** —— 用户可以随便改写描述或加注解
- 只执行仍处于勾选状态的条目（支持部分批准）
- `aiPlan` 记录 `snapshot`（涉及文档的 `id` + `updatedAt`）与 `folderBaseline`（文件夹表基底）
- 执行前逐条比对：任一失配即**中止并要求重新生成**，绝不在陈旧计划上行动

## 建议清理 = 归入待清理目录，永不删除

AI 可以提议某些文档已无保留价值（`suggest-cleanup` 条目，每条附理由）。这些条目 MUST 单独成节，
节前 MUST 显式说明后果。被批准执行时，其语义是**把文档归入名为 `_待清理` 的普通文件夹**，
MUST NOT 调用任何删除接口 —— 删不删由用户在这之后自己决定。

`_待清理` 是普通文件夹（可改名、可删、可搬东西出来），不享有 AI 空间那样的保护语义，并计入目录总数。

## 候选集边界

- 记忆文档与 AI 空间里的一切**不进候选集**，也不会出现在计划的任何条目里
- 只看当前项目的文档；跨项目的归类不在本技能范围
- 同一篇文档同时被提议归类与清理时，以归类为准（两条并存会读成互相矛盾的指令）

## 遇到不一致的既有数据

孤儿文件夹（`projectId` 指向已不存在的项目）、重名文件夹等异常，MUST **只在计划的
「只报告，不处置」区如实列出**，MUST NOT 自动删除、合并或改写。首次跑整理时这是最容易出事的地方 ——
一个「聪明」的 agent 很可能顺手把用户的数据清理掉。

## `/api` 依赖

| 端点 | 用途 |
| --- | --- |
| `GET /api/health` | 探活 |
| `GET /api/documents?fields=meta` | 列待归类文档（不取正文） |
| `GET /api/document-folders` | 列现有文件夹（含 AI 空间） |
| `GET /api/document-projects` | 判定孤儿文件夹 |
| `POST /api/documents` | 落计划文档 |

执行阶段（用户批准后）另用 `POST /api/document-folders`（只增不改删）与 `PUT /api/documents/:id`（只改归属）。

## 边界

- 本技能到**产出计划**为止，不改动任何文档。
- AI 不删除文档或文件夹；「清理」的执行语义是归入待清理目录，删除只能由用户自己做。
- 不提议改名或合并既有文件夹。
- 文件夹写入只增不改删，且写前重读为基底 —— 文件夹表是整表覆写且无并发控制。
- LLM 由消费者自备（内部 = 客户端 `src/app/llm.ts`；外部 agent = 自带）。
